Smart contract คือโปรแกรมที่ประมวลผลเงื่อนไขบนเครือข่าย blockchain เมื่อข้อมูลนำเข้าตรงตามกฎที่กำหนด โปรแกรมจึงบันทึกสถานะหรือเรียกการทำงานที่เตรียมไว้ ชื่อนี้อาจทำให้นึกถึงสัญญาทางกฎหมาย แต่โค้ดไม่ได้ตีความเจตนา ข้อยกเว้น หรือบริบทได้เอง ทุกอย่างขึ้นอยู่กับกฎและข้อมูลที่ระบบได้รับ

ในงานสุขภาพ smart contract มักถูกเสนอให้ใช้กับการให้สิทธิ์ การชำระเงิน ห่วงโซ่อุปทานยา และการวิจัย แต่การเป็นกรณีใช้งานที่เป็นไปได้ไม่เท่ากับการติดตั้งจริง บทความนี้จึงแยกแนวคิดทั่วไปออกจากขอบเขตที่ยืนยันได้ของ HealthTAG

## กฎแบบ if-then ทำงานอย่างไร

เงื่อนไขพื้นฐานของ smart contract เขียนได้ในรูป "ถ้าเงื่อนไขเป็นจริง ให้ทำรายการที่กำหนด" เช่น ถ้าสถานะสิทธิ์ยังมีผล ระบบจึงยอมรับคำขอในขั้นถัดไป เครือข่ายประมวลผลกฎเดียวกันและเก็บผลไว้ในประวัติธุรกรรม

ความสม่ำเสมอนี้มีประโยชน์กับกฎที่กำหนดได้ชัด แต่ไม่ได้รับประกันว่ากฎนั้นถูกต้อง หากเขียนเงื่อนไขผิด ใช้ข้อมูลจากแหล่งที่ไม่น่าเชื่อถือ หรือไม่รองรับเหตุฉุกเฉิน ระบบก็อาจทำงานผิดอย่างสม่ำเสมอ การตรวจทานโค้ด การควบคุมข้อมูลนำเข้า และวิธีแก้ไขเมื่อพบข้อผิดพลาดจึงยังจำเป็น

## การให้ความยินยอมและสิทธิ์เข้าถึง

กรณีใช้งานที่เกี่ยวข้องกับ HealthTAG มากที่สุดคือการจัดการสถานะสิทธิ์ ผู้ป่วยหรือกระบวนการที่ได้รับอนุญาตกำหนดช่วงเวลาการเข้าถึง จากนั้นระบบปลายทางตรวจสถานะก่อนส่งข้อมูล

ในสถาปัตยกรรมปัจจุบัน Hospital API ตรวจช่วงเวลา 15 นาทีที่กำหนดจากสถานะบน blockchain หากคำขอผ่านจึงอ่านข้อมูล FHIR จากระบบโรงพยาบาล Blockchain เก็บเหตุการณ์การให้ความยินยอมและการเข้าถึง ส่วนเวชระเบียนยังอยู่ใน FHIR Server ที่โรงพยาบาลควบคุม

ขอบเขตนี้ต่างจากการนำเวชระเบียนไปเก็บใน smart contract ข้อมูลทางคลินิกมีรายละเอียดมาก เปลี่ยนแปลงตามการรักษา และอยู่ภายใต้การควบคุมของโรงพยาบาล ระบบจึงส่งข้อมูลผ่าน API หลังตรวจสิทธิ์ แทนการเผยแพร่ข้อมูลลงในบัญชีแยกประเภท

## การเคลมประกันเป็นแนวคิดที่ต้องเชื่อมหลายระบบ

Smart contract อาจถูกออกแบบให้ตรวจข้อมูลกรมธรรม์ เอกสารการรักษา หรือสถานะการอนุมัติก่อนเริ่มขั้นตอนชำระเงิน แต่ blockchain ไม่รู้ข้อเท็จจริงภายนอกด้วยตนเอง ระบบต้องมีแหล่งข้อมูลที่เชื่อถือได้ รวมทั้งวิธีรับมือกับข้อมูลผิด ข้อยกเว้น การอุทธรณ์ และข้อกำหนดของหน่วยงานกำกับ

ตัวอย่างทั่วไปอาจเริ่มจากระบบโรงพยาบาลส่งรหัสการวินิจฉัยและรายการเรียกเก็บเงินไปยังบริการที่ตรวจสอบข้อมูล จากนั้น oracle ส่งสถานะที่จำเป็นให้ smart contract เปรียบเทียบกับเงื่อนไขกรมธรรม์ หากเงื่อนไขครบ ระบบจึงเริ่มขั้นตอนอนุมัติหรือชำระเงินต่อไป หากข้อมูลขัดแย้งกัน เคสต้องเข้าสู่กระบวนการตรวจสอบของคน

ระบบลักษณะนี้อาจลดเวลาที่เสียไปกับการส่งเอกสารและการตรวจเงื่อนไขซ้ำ แต่ระยะเวลาจริงขึ้นอยู่กับบริษัทประกัน คุณภาพข้อมูล การตรวจทุจริต และกฎที่ใช้ จึงไม่ควรกำหนดว่าทุกกระบวนการจะเสร็จภายในไม่กี่นาที

การเคลมอัตโนมัติเป็นตัวอย่างทั่วไปของ smart contract ขอบเขต HealthTAG ที่ยืนยันได้ในปัจจุบันครอบคลุมการอนุญาตและประวัติการเข้าถึง

## ห่วงโซ่อุปทานและการวิจัยก็ต้องมีหลักฐานแยกกัน

แนวคิดเดียวกันอาจใช้ตรวจเงื่อนไขการขนส่งยา หรือบันทึกสถานะการทำงานในโครงการวิจัยได้ แต่ sensor ผู้รับรอง และกระบวนการภายนอกยังเป็นผู้สร้างข้อเท็จจริง Smart contract ทำได้เพียงประมวลผลข้อมูลที่ได้รับตามกฎ

ในห่วงโซ่อุปทาน กฎอาจตรวจว่าอุณหภูมิระหว่างขนส่งอยู่ในช่วงที่กำหนด มีใบรับรองจากหน่วยงานที่ระบุ และผู้รับยืนยันการส่งมอบแล้ว จากนั้นระบบจึงปล่อยการชำระเงินหรือบันทึกว่างานขั้นนั้นเสร็จสมบูรณ์ ตัวอย่างนี้ต้องพึ่ง sensor และผู้รับรองที่เชื่อถือได้ เพราะ smart contract ไม่สามารถยืนยันสภาพของยาได้ด้วยตนเอง

ในงานวิจัย กฎอาจบันทึกว่าผู้เข้าร่วมทำขั้นตอนตามโครงการครบแล้ว และเริ่มการจ่ายค่าตอบแทนตามข้อตกลง ข้อมูลผลการทดลองยังต้องเก็บในระบบที่เหมาะกับข้อมูลวิจัย การอนุมัติด้านจริยธรรม การถอนความยินยอม และการแก้ไขข้อมูลยังอยู่ภายใต้กระบวนการของโครงการ

ตัวอย่างเหล่านี้อธิบายความเป็นไปได้ของเทคโนโลยี ส่วนรายละเอียดของผลิตภัณฑ์ การติดตั้ง หรือความร่วมมือของ HealthTAG ต้องอ้างอิงหลักฐานเฉพาะของงานนั้นโดยตรง

## Smart contract ไม่แทนการตัดสินใจของคน

กฎอัตโนมัติเหมาะกับเงื่อนไขที่วัดและตรวจซ้ำได้ แต่ระบบสุขภาพมีบริบทที่โค้ดอาจไม่เห็น เช่น เหตุฉุกเฉิน ความคลาดเคลื่อนของตัวตน หรือข้อมูลที่ยังไม่ครบ การออกแบบจึงต้องกำหนดผู้รับผิดชอบ ช่องทางทบทวน และขั้นตอนจัดการข้อผิดพลาด

ความโปร่งใสของประวัติไม่ได้หมายความว่าควรเปิดข้อมูลทุกอย่าง ผู้พัฒนาต้องลดข้อมูลที่บันทึกบน blockchain ให้เหลือเท่าที่จำเป็น ปกป้องข้อมูลในระบบต้นทาง และให้สิทธิ์แก่ผู้ใช้อย่างเหมาะสมกับหน้าที่

## ขอบเขตที่ควรจำเกี่ยวกับ HealthTAG

HealthTAG ใช้ blockchain เป็นชั้นสำหรับสถานะสิทธิ์และประวัติการให้ความยินยอมกับการเข้าถึง โรงพยาบาลยังควบคุมเวชระเบียน Hospital API ตรวจสิทธิ์ และข้อมูลทางคลินิกเดินทางผ่าน FHIR API เมื่อคำขอได้รับอนุญาต

การอธิบาย smart contract อย่างรับผิดชอบจึงต้องระบุทั้งสิ่งที่โค้ดทำและสิ่งที่อยู่นอกขอบเขต มันช่วยให้กฎบางประเภททำงานสม่ำเสมอและตรวจย้อนหลังได้ แต่ไม่ได้ทำให้ข้อมูลนำเข้าถูกต้อง ไม่ได้แทนการกำกับดูแล และไม่ได้เปลี่ยน blockchain ให้เป็นที่เก็บเวชระเบียน
